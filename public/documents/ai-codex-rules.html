AI / Codex Rules

Mandatory Read before making any changes Last updated: September 2026

Development rules and guidelines for AI assistants working on the AquaDealers codebase. Following these rules prevents regressions, duplicated code, and broken business logic.

Before Changing Anything

Complete all 11 checks before writing any code. Skipping these is the #1 cause of regressions.
1
Inspect existing architecture. Read App.tsx for routes. Check the feature directory structure under src/features/. Understand where the change belongs.
2
Find existing implementation. Grep before writing new code. The codebase has 27 modals, 33 forms, and extensive utilities. Whatever you need probably exists already.
3
Reuse existing components. Check src/components/ui/ (23 components). Button has 9 variants, Card has 5, Modal has focus trap + portal. Don't create new UI primitives.
4
Check related workflows. A bill change affects: inventory (FIFO lots), farmer.total_due (triggers), cash_book, payment_allocations, transaction_events. Map the full impact before editing.
5
Check mobile AND desktop. Layout split at lg: (1024px). Billing has separate mobile (3-step wizard) and desktop (2-step side-by-side) flows. Test both.
6
Check permissions. FeatureGate gates features by subscription plan. Staff permissions are JSONB-based. Both may need updating for new features.
7
Check database impact. Core writes go through RPCs (create_bill_v2, process_return, etc.). Never bypass RPCs with direct inserts — they skip validation, triggers, and audit trails.
8
Check business rules. Financial calculations must match RPC logic exactly. GST is per-item (not flat). Farmer due is trigger-recalculated. Don't duplicate calculation logic.
9
Check edge cases. Cancellation: same-day + unpaid only. Stock: never goes negative. Walk-in: full payment required. Credit limit: warning, not block.
10
Test the implementation. Run npm test (Vitest unit tests) and npm run test:e2e (Playwright). Test at both mobile and desktop viewports.
11
Update documentation when behavior changes. Keep docs pages in public/documents/ current.

Never Do

Hard rules. No exceptions.
  • Duplicate functionality. Check the 27 modals and 33 forms first. Search for existing hooks, utils, and service functions before creating new ones.
  • Invent requirements. Build what was asked for, nothing more. No speculative features, no "while I'm here" additions.
  • Remove existing features without explicit approval from the product owner.
  • Change financial logic casually. Billing, payment allocation, FIFO consumption, and GST calculation are critical paths. Any change requires understanding the full RPC chain.
  • Update a product's price by writing only inventory.selling_price/mrp. Once a product has stock, Billing and the Stock list both price it from the FIFO lot (getNextSellingLot in src/features/inventory/utils/pricing.ts), not the inventory row. Any price-editing code must update the active lot too (see inventory-logic.html) or the edit will silently not take effect for existing stock — this exact bug shipped and went unnoticed until 2026-09-15.
  • Expose secrets. Note: SUPABASE_ANON_KEY in supabase.ts is intentionally public (it's a publishable key). The service_role key must never appear in client code.
  • Bypass authorization. Always use supabase.rpc() for writes. Direct table inserts/updates skip validation, triggers, and audit logging.
  • Create inconsistent UI patterns. Use the design system: design tokens for colors, sonner for toasts, Modal for dialogs, Button variants for actions. No one-off styled components.
  • Add dependencies without justification. Check if the functionality exists in the stdlib, platform, or already-installed packages first.

Critical Data Flow

Bill Creation Flow

User selects products → useCheckout builds payload (incl. a fresh idempotency_key per submit attempt) → supabase.rpc('create_bill_v2', payload) → RPC checks (dealer_id, idempotency_key) first and returns the existing bill if already present, otherwise atomically: validates stock, consumes FIFO lots, creates bill + items, allocates payment, updates farmer.total_due via trigger, logs transaction event → React Query cache invalidated → PDF generated client-side → optional WhatsApp notification.

Offline Sync Flow

Bill queued offline gets its own client_ref UUID (minted when it's queued, not reused from any earlier online attempt) → stored in IndexedDB → on reconnect, create_bill_offline_sync(payload, client_ref) is called → it checks for an existing bill with that client_ref first and returns it if found, otherwise calls create_bill_v2(payload), which does its own dedupe by idempotency_key (see above) before inserting, then stamps the new client_ref onto whichever bill it returned. This two-layer check is what prevents a duplicate bill when an online submit actually committed but its response was lost (see 20260917000001_bill_v2_idempotency_key.sql / Glossary: idempotency_key) — client_ref alone can't catch that case because the retry always mints a new one.

Product Pricing Flow

Dealer edits price in EditInventoryModal → writes inventory.selling_price/mrp/medicine_discount_percentage (the fallback default) and the current FIFO lot's inventory_lots.selling_price/mrp/medicine_discount_percentage/final_unit_price (what actually gets charged) in the same save → both Billing (ProductSelector) and the Stock list read the FIFO lot's price via getNextSellingLot/getInventoryDisplayPrice, falling back to the inventory row only when a product has no active lot. See Which Price Actually Gets Charged? for the full explanation.

Deliberately not synced: cost_price. The item-level value is "latest purchase cost" (a quick-reference default); the lot-level value is that specific batch's real historical cost for COGS, and can legitimately differ from the latest purchase. EditInventoryModal only pushes retail-facing fields to the lot — never cost_price. Only the dedicated per-lot editor on InventoryDetailPage (the "Lots" tab) should change a lot's cost_price, since that's an intentional, batch-specific correction, not a side effect of fixing a selling price.
