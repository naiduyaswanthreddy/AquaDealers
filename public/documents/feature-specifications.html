Billing (Core)

Billing is the primary feature of AquaDealers. Every bill creates a cascade of data changes across multiple tables in a single atomic transaction.

Atomic Save: create_bill_v2 RPC

A single PostgreSQL function that performs all of the following in one transaction. If any step fails, the entire transaction is rolled back — no partial state.

#OperationTable
1Insert bill header (number, date, farmer, totals, branch)bills
2Insert line items with quantities, rates, discountsbill_items
3Deduct stock from oldest FIFO lots per iteminventory_lots
4Record inventory movements (type: 'sale')inventory_movements
5Insert payment record (if amount_paid > 0)payments
6Allocate payment to this billpayment_allocations
7Create cash book entry (if cash payment)cash_book
8Update farmer due balance (via trigger)farmers
9Record transaction event for undo capabilitytransaction_events

Offline Sync

When the device is offline, bills are saved locally and synced when connectivity returns. The sync mechanism uses create_bill_offline_sync RPC with client_ref idempotency.

Idempotency

Each offline bill gets a client_ref — a UUID generated on the client when it is queued for offline sync. There is a unique index on (dealer_id, client_ref) on the bills table, and create_bill_offline_sync checks it before inserting, so re-running the sync queue never double-creates a bill.

client_ref alone does not cover every duplicate path: if an online create_bill_v2 call actually commits but its response is lost (e.g. on a flaky connection), the client cannot tell the difference from a request that never reached the server, and falls back to the offline queue with a new client_ref — which would slip past the client_ref check. To close this, every checkout also generates an idempotency_key once per submit attempt, which survives that fallback unchanged (same payload object, same key). create_bill_v2 itself checks (dealer_id, idempotency_key) first and returns the existing bill instead of inserting a duplicate — so the direct path and the offline-fallback path are both covered, no matter which client_ref the retry ends up using. A partial unique index on (dealer_id, idempotency_key) (ignoring nulls) backs this the same way.

create_bill_offline_sync propagates create_bill_v2's dedupe result into its own already_synced flag, not just its own client_ref check — otherwise a bill deduped via idempotency_key (new client_ref, pre-existing bill) would look "freshly synced" to the client and re-trigger the send-bill-whatsapp notification for a bill the farmer was already sent.

Draft Tabs

Up to 5 concurrent drafts stored in sessionStorage. Each draft preserves:

  • Selected farmer
  • Added products with quantities, rates, discounts
  • Payment amount and method
  • Any notes

Drafts survive page refreshes within the same browser tab but not across tabs or after closing the browser.

PDF Generation

  • Bills: html2canvas renders the invoice DOM to a canvas, converts to PNG, then embeds in a jsPDF document. This ensures the PDF matches the on-screen invoice pixel-for-pixel.
  • Reports/Statements: Programmatic jsPDF — directly draws text, tables, and lines for consistent layout regardless of screen rendering.

Bill Numbering

Format: AD-{YYYYMMDD}-{sequence}

The sequence is a branch-specific auto-incrementing counter. Example: AD-20260909-042 is the 42nd bill from this branch on September 9, 2026.

Returns

Returns handle the reversal of sold goods. There are two entry points that both restore stock and adjust balances, but differ in scope:

  • Bill-first (create_bill_return): return against one specific bill, started from Bill Details.
  • Farmer-first (create_farmer_return_v1): return started from the farmer, spanning a date range across that farmer's bills; the server auto-allocates the returned quantity across the matching bill_items (most recent bill first) and reports any leftover as an "unmatched" line at a dealer-entered price.

Database Tables

  • bill_returns — shared header for both flows: linked bill (bill-first) or farmer + date range (farmer-first), return date, total amount, settlement method
  • bill_return_items — bill-first line items: product, quantity returned, bill_item_id
  • farmer_return_lines — farmer-first line items: product, requested/matched/unmatched quantity, unmatched price
  • bill_return_allocations — farmer-first: how a farmer_return_lines row was split across specific bill_items (one row per bill hit)

Both bill_return_items.bill_item_id and bill_return_allocations.bill_item_id are what get_farmer_items_v1/get_farmer_item_bills_v1 sum up to net returned quantity/value out of the farmer's purchase totals (see below) — a return only ever reduces a bill_item's effective quantity for reporting, it never edits the original bill_items row.

Stock Restoration

Bill-first returns restock the same lots the sale consumed, walked in the same order they were consumed (earliest-consumed lot first — i.e. FIFO order, not LIFO), via bill_item_lot_allocations. If a lot record is gone, restocking falls back to the inventory row's quantity_in_stock directly.

Farmer-first returns aren't tied to specific bill_item_lot_allocations rows (a farmer-first return spans a date range, not one bill), so they can't restock the original lot(s). Instead the returned quantity goes into one synthetic inventory_lots row per product per branch, batch_number = 'CUSTOMER-RETURN', shared across every farmer-first return of that product — a later return tops up the same lot's quantities rather than creating a new one. See Inventory Logic: the CUSTOMER-RETURN lot.

Fixed 2026-09-17: the 2026-08-17 rate-limit-bypass migration for create_farmer_return_v1 was rewritten from an older copy of the function and lost the shared-lot reuse above — undo_transaction_v1 still assumed it (decrementing the lot rather than deleting it), but every new farmer-first return on a product with a prior return created a second CUSTOMER-RETURN lot instead of topping up the first. That also meant the lot's mrp/selling_price were never set (only ever true for this batch — the fields aren't populated on insert), so Billing's batch picker showed the returned stock's quantity split across duplicate rows and its price as ₹0. Separately, and unrelated to this regression: ProductSelector's "Add to Bill" was assuming getLotsWithStock() returns lots newest-first and read it back-to-front to find the oldest one with room — but it actually returns oldest-first (FIFO), so the reversed read picked the newest lot instead, most visible once a product had a recent, differently-priced CUSTOMER-RETURN lot in the mix. Both are fixed: the RPC restores the shared-lot reuse and seeds pricing from the inventory row (existing null-priced lots were backfilled; existing duplicate lots from the affected window were left alone rather than merged, to avoid corrupting their undo history), and lot selection now walks getLotsWithStock() in its actual order via a small, unit-tested pickLotWithCapacity() helper in src/features/inventory/utils/pricing.ts.

Excess Returns and Credit

How the excess (return value beyond what's owed) is handled differs by flow:

  • Bill-first: the bill's balance_due is clamped at 0; any excess just lets farmers.total_due go negative (rendered as a negative balance). return_credit_balance is not touched.
  • Farmer-first: excess is resolved by the dealer's chosen settlement_method — farmer_credit adds to farmers.return_credit_balance (applied to the farmer's next bill), or cash_refund logs an expense in cash_book instead.

Audit Trail

Every return creates inventory movement records (reference_type = 'bill_return' for bill-first, 'farmer_return' for farmer-first) pointing to the return, plus a transaction_events row so it shows up in and can be undone from /transactions.

Fixed 2026-09-16: get_farmer_items_v1 and get_farmer_item_bills_v1 (the farmer detail page's Items tab and its per-item bill drilldown) used to sum bill_items directly with no idea returns existed, so a farmer's purchased quantity/value never dropped after a return — stock correctly went back up, but the farmer-facing numbers were stuck at pre-return values indefinitely. Both RPCs now subtract bill_return_items + bill_return_allocations per bill_item before aggregating. Bills, statements, the ledger, and farmer due totals were never miscalculated by this bug — bills.balance_due/farmers.total_due are updated directly by the return RPCs, independent of these two aggregation functions.
Fixed 2026-09-17: even though the numbers above were always correct, returns were effectively invisible everywhere they should show up. The Bill History list (/bills) and the farmer's own Bills tab (/farmers/:id) showed no indicator at all — no badge, no column — for any bill with a return, in either the desktop table or the mobile card. Bill Details (/bills/:id) only showed a return in a card at the very bottom of the page with no indicator above the fold, and its per-item "N sold − M returned" note only counted bill_return_allocations, silently missing bill-first returns recorded in bill_return_items on the same line. A farmer's Ledger tab return entries were not clickable at all — no way to see what was actually returned without leaving the page. The Balance Statement PDF (getFarmerStatement() + farmerStatementPdf.ts) fetched only the bill_returns header with no line items from either return table, and its template only ever printed an amount for bill/payment rows — a return row showed -/N/A in both amount columns despite the running balance visibly dropping. A farmer's Ledger tab return entries now open a read-only item/amount breakdown on click. The statement lists each return's items and prints its amount (in amber) in the PAID(-) column instead of a blank placeholder. getFarmerReturnDetail() now merges items from both farmer_return_lines and bill_return_items.

Stock Transfers

Transfer stock between branches while preserving FIFO lot data. Each transfer creates movement records at both ends.

How It Works

1
Select source branch and product — shows available lots at that branch
2
Select destination branch — must be a different branch owned by the same dealer
3
Enter quantity — cannot exceed available stock at source
4
Execute via create_stock_transfer RPC

What the RPC Does

  • Deducts from source lot(s) using FIFO order
  • Creates new lot(s) at destination with the same cost, expiry, and supplier data
  • Creates inventory movement at source: type = 'transfer_out'
  • Creates inventory movement at destination: type = 'transfer_in'
  • Both movements reference each other via reference_id
FIFO Preservation: If transferring 100 units and the source has Lot A (80 units, Jan expiry) and Lot B (50 units, Mar expiry), the transfer creates two lots at the destination: 80 from Lot A and 20 from Lot B, preserving the original cost and expiry dates.

Bill Editing

RPC: edit_bill_v1

What Can Be Edited

  • Quantities (increase or decrease)
  • Unit prices
  • Discounts (per-item)
  • Bill date
  • Payment amount
  • Payment type

Stock Adjustment Logic

  • Quantity decreased: Stock is restored using LIFO (same as returns)
  • Quantity increased: Additional stock is consumed using FIFO (same as new billing)
  • Product removed: Full stock restoration for that item
  • Product added: Full FIFO consumption for the new item

Audit Trail

Every edit creates a record in bill_audit_logs with:

  • Before state: Complete snapshot of the bill before the edit (items, amounts, payments)
  • After state: Complete snapshot after the edit
  • Changed by: User/staff who made the edit
  • Timestamp

The bill record itself is flagged with is_edited = true so edited bills are visually distinguished in bill history.

Bill Cancellation

RPC: cancel_bill_v1

Constraints

ConstraintRuleReason
TimingSame-day onlyPrevents backdated financial manipulation
Paymentamount_paid must be 0Bills with payments must be handled via returns or editing
StatusMust not already be cancelledIdempotency — returns 'already_cancelled' without error

What Cancellation Does

  1. Sets bill status = 'cancelled'
  2. Restores all stock to original FIFO lots (LIFO restoration)
  3. Reduces farmer outstanding balance by the bill amount
  4. Creates inventory movements with reference_type = 'cancellation'
  5. Records transaction event for audit
Idempotent: Calling cancel_bill_v1 on an already-cancelled bill returns 'already_cancelled' status without error or side effects. Safe to retry.

Transaction Undo

A universal undo system that covers all financial transactions in the application.

Supported Transaction Types

TypeUndo Behavior
BillsCancels the bill, restores stock, reverses farmer due
PurchasesRemoves inventory lots, reverses supplier balance
Payments (farmer)Reverses payment allocation, restores farmer due
Supplier PaymentsReverses payment, restores supplier balance
ReturnsRe-deducts returned stock, reverses farmer credit
Stock TransfersReverses transfer at both branches
ExpensesRemoves expense record and cash book entry
Manual Cash EntriesRemoves the entry from cash book

How It Works

  • Table: transaction_events records every financial transaction with type, reference ID, timestamp, and actor
  • Window: 48 hours from creation. After 48 hours, the undo option disappears.
  • RPC: undo_transaction_v1
  • Method: Soft-delete using deleted_at or cancelled_at timestamps rather than hard deletion. This preserves the audit trail — undone transactions are still visible but marked as undone.
48-Hour Window: The undo window is enforced server-side in the RPC. The UI hides the undo button after 48 hours, but even if called directly, the RPC rejects undo attempts outside the window.
